# Блок прогноза

`forecast-fetcher` получает время Open-Meteo в `LOCATION_TIMEZONE` и сохраняет его с этим часовым поясом. API и оба бота используют тот же пояс для границ суток при запросе дневного прогноза. Для совместимости скорость ветра сохраняется в канонической единице Open-Meteo км/ч (`wind_speed_unit=kmh`); `ForecastService` преобразует её в м/с для веба, API и ботов.

В веб-блоке без раскрытия показываются:

- почасово: количество и вероятность осадков; ветер и порывы только от 10/15 м/с; «ощущается» только при разнице с температурой от 3 °C;
- по дням: компактная вторая строка с осадками, максимальным ветром/порывами и максимальным UV. Отсутствующее значение обозначается `—`, а не нулём;
- одна короткая сводка только для свежего прогноза: сначала вероятные осадки, затем сильные порывы, затем изменение температуры.

Старые строки базы совместимы и по схеме, и по единице измерения: fetcher теперь лишь фиксирует уже используемую единицу явным параметром.

## Переход часового пояса

После исправления timestamp дневные точки новых загрузок могут пересекаться по абсолютному времени со старыми точками, записанными как UTC. Никакие строки и миграции не удаляются: `SaveBatch` сохраняет один fetch атомарно, а чтение hourly и daily выбирает только поколение с максимальным `fetched_at` для соответствующего типа. Поэтому веб, API и боты не смешивают старое и новое поколение, в том числе на границе горизонта прогноза.

Специальные cleanup или миграция для перехода не нужны: обычное удаление данных старше 7 дней остаётся в fetcher. Перед production-обновлением нужен снимок **только `forecast_data`**; при откате восстанавливайте только эту таблицу, чтобы не затронуть параллельных collectors. После обновления дождитесь успешной записи `forecast fetched and saved successfully`, затем убедитесь, что `MAX(fetched_at)` свежий и что в дневном прогнозе нет повторяющихся календарных дат в `LOCATION_TIMEZONE`.
